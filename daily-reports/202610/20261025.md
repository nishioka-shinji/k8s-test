# 2026-10-25

## kiali / prometheus / flux-system を Istio ambient に参加させる

- Kiali の Namespace グラフで kiali を選ぶと何も出なかった。kiali namespace がメッシュ外のため、ingress-istio → kiali の通信には送信側（reporter="source"）のメトリクスしかなく、Kiali が受信側として描けるデータがなかった
- 稼働中の Pod を可能な限り ambient に入れる方針にし、kiali / prometheus / flux-system の namespace に参加ラベルを付けた（PR #13）。flux-system の Namespace は flux install の生成物なので、直接編集せず Kustomization の patches でラベルを付けた
- 対象外にしたもの: kube-system / istio-system（Istio が除外）、istio-ingress（Gateway の Pod は Istio が dataplane-mode: none にする）、local-path-storage（manifests の管理外）、hostNetwork の Pod
- kiali を ambient に入れた直後、kiali.localhost が 503 / タイムアウトになった。kiali-server chart が既定で作る NetworkPolicy が受信を 20001 / 9090 に絞っていて、ambient の HBONE（TCP 15008）を遮断していた。chart の NetworkPolicy は残し、15008 を許可する NetworkPolicy を追加して解消した。flux-system も付属の NetworkPolicy が特定ポートしか許可しないため同様に追加した。kube-prometheus-stack は現在の values では NetworkPolicy を作らないので追加していない
- 稼働中の Pod は再起動なしで ambient に入った。反映直後に istio の Kustomization が API server への接続 reset で一度失敗したが、reconcile し直して解消した。通信中の接続が切られたためと推測している
- 実装は Orca のワーカーに任せた。マージ後に main を push し直し、全 Kustomization の Ready、kiali.localhost の応答、Kiali graph API で kiali namespace の node と辺が返ることを確認した

### 申し送り

- ambient で Ingress のポートを絞る NetworkPolicy がある namespace では、15008 も許可しないと通信が止まる。chart が NetworkPolicy を作るアプリを ambient に入れるときは確認が要る
- waypoint はどこにも置いていないため、ingress-istio を経由しない ambient Pod 同士の辺（curl → httpbin、prometheus → alertmanager、Flux の controller 間など）は L4（TCP）だけで描かれ、HTTP の rps や成功率は出ない。L7 の機能を使う場所がないので、waypoint は当面置かない判断にした
- Prometheus の down ターゲット 6 件（kube-proxy ×3、etcd、scheduler、controller-manager）は ambient 化の前から down だった

## クラスタ外への宛先を ServiceEntry で名前付きにする istio-external を追加

- flux-system の source-controller からの通信が Kiali で unknown 宛てと表示されていた。宛先はクラスタ外の kind-registry と Helm リポジトリ群で、メッシュ内の Workload でも Service でもないため名前が付かない
- 表示のためだけでも、どこにアクセスしているかを可視化しておきたいという方針で、宛先ごとに ServiceEntry を置くアプリ istio-external を追加した（PR #14）。egress の制限や waypoint の追加はしない
- 対象は kind-registry、blob.istio.io とそのリダイレクト先 istio-release.r2.istio.io、kiali.org、prometheus-community.github.io、github.com、release-assets.githubusercontent.com、grafana.com。送信元は source-controller、kustomize-controller、grafana
- ServiceEntry は addresses を書かず、istiod の自動割り当て VIP と ztunnel の DNS キャプチャで宛先を識別させた。どちらも Istio 1.31 の既定で有効なので istio 側の設定は変えていない
- ServiceEntry の CRD は istio が入れるため、常時同期の flux-system には置かず、dependsOn: istio の独立したアプリとして宣言した
- 最初の反映で blob.istio.io 宛てが一部 unknown のまま残った。blob.istio.io の index.yaml が istio-release.r2.istio.io へリダイレクトされていたためで、ServiceEntry を追加して解消した
- 実装は Orca のワーカーに任せた。DNS 応答が VIP に変わる経路変更で kind-registry からの取得が壊れないかを重点的に見て、Flux のソースと全 Kustomization が Ready のまま、ztunnel のアクセスログと Prometheus で各宛先にホスト名が付くこと、Kiali に ServiceEntry のノードが出ることを確認した。マージ後に main を push し直して再確認した

### 申し送り

- ambient では ServiceEntry の exportTo が ztunnel に効かず、メッシュ全体から見える
- 新しい外部宛先が増えたら istio-external に ServiceEntry を足す。リダイレクト先のホストも別途必要になる
- Prometheus がメッシュ外のターゲット（coredns、istiod / istio-cni-node、ノード上のコンポーネント）をスクレイプする通信は、クラスタ外ではないので対象外にした。Kiali では引き続き unknown や PassthroughCluster として見える
