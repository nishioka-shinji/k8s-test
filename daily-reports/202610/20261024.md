## Flux を作り直しローカルレジストリの OCIRepository から同期する構成に変更

- kind クラスタの Flux は bootstrap 未完了で、GitRepository / Kustomization / deploy key の Secret がなく main を同期できていなかった。GitRepository の URL も Flux が受け付けない scp 形式だった
- GitHub ではなくローカルから反映したいので、kind 公式の Local Registry 手順に沿ってレジストリ kind-registry を立て、手元の作業ツリーを OCI artifact として push して OCIRepository で同期する構成にした（PR #4）
- source-controller は Pod 内からレジストリを直接読むため、containerd の hosts.toml 設定（公式手順のステップ 2・3）は不要と判断し、既存クラスタを作り直さずに後付けした
- flux CLI を mise で v2.9.6（バージョン明示）に入れ、クラスタの Flux を v2.4.0 から v2.9.6 に作り直した
- 同期を始めると imgproxy-2 の ServiceMonitor が prometheus（kube-prometheus-stack）の入れる CRD 待ちで止まり、同期全体が進まなくなった。CRD・webhook の提供元と利用側を別々の Flux Kustomization に分け、dependsOn で適用順を付けて解消した（cert-manager → openfeature → openfeature-demo、prometheus → imgproxy-2）
- 実装は Orca のワーカーに任せた。切り替え後、Flux の Kustomization 6 つと HelmRelease 2 つ（authentik / kube-prometheus-stack）がすべて Ready になったことを確認した

### 申し送り

- flux uninstall で authentik の HelmRelease が消えたため、kubectl apply -k authentik で入れ直した。Flux を作り直すときは、Flux 管理外で入れた HelmRelease を入れ直す必要がある
- 同期元が手元からの push になったので、PR をマージしてもクラスタには反映されない。反映は flux push artifact で行う
- kind v0.33.0 のノードでも containerd の registry config_path は空だった。自作イメージを localhost:5001 から Pod で pull する場合は、公式手順のステップ 2・3 が必要か別途確認が要る

## アプリの同期を Flux Kustomization の宣言方式に統一

- アプリの入口がルートの kustomization と Flux Kustomization（適用順序付き）の 2 系統に分かれていて構成が追いにくかったため、ルートは flux-system だけを束ね、アプリは Flux Kustomization に一本化した（PR #5）
- テスト環境なので全アプリを常時同期するのはやめ、検証したいアプリだけを Flux Kustomization として宣言して使う方式にした。既定では何も同期しない
- 宣言時の書き方と、CRD・webhook の依存があるアプリの組み合わせ（cert-manager → openfeature → openfeature-demo、prometheus → imgproxy-2 の wait / dependsOn）は flux-system の README に残した。SMTP・forward auth・API 呼び出しのような実行時通信だけの依存には dependsOn を付けない方針にした
- Flux はルート Kustomization の中で子 Kustomization の作成と旧リソースの prune を同じ reconcile で行うため、一度に移すと authentik namespace（手作業の Secret・PVC）や unleash-db が消える。prune: disabled を使う段階移行も検討したが、検証用クラスタなのでデータ消失を許容して見送った
- 実装は Orca のワーカーに任せた

## マニフェストを manifests ディレクトリに集約し検証コマンドを全アプリに拡充

- アプリ（namespace）ごとのディレクトリと日報が同じ階層に並んでいたため、マニフェスト系を manifests にまとめ、OCI artifact として push するのを manifests だけにした。日報や .git を除外指定で外す必要がなくなった
- artifact のルートが manifests になるので、Flux 側の同期パス（OCIRepository を読む Kustomization とアプリ宣言の path）は変えずに済む構成にした
- 検証コマンドは authentik / caddy-demo だけを個別に build していたため、apps.yaml が空の既定状態では他のアプリが壊れても気づけなかった。manifests 配下の全ディレクトリを kustomize build するループに置き換えた
- infrastructure / apps への分割は、ディレクトリ数が少ないうちは不要と判断して見送った
- 実装は Orca のワーカーに任せた

## Istio を ambient モードで Helm と Flux から導入

- ambient モードを検証するため、Istio 1.31.3 を HelmRelease（base → istiod → istio-cni → ztunnel を dependsOn で順序付け）で入れた。istiod と istio-cni は ambient プロファイル（PR #7）
- 旧 Helm リポジトリ（storage.googleapis.com）は 1.30 系までしかないため、公式手順が案内する新リポジトリ（blob.istio.io）を使った
- Gateway API の CRD は公式 1.31 手順では experimental 版だが、waypoint を使うには standard 版で足りるため standard v1.6.0 にした
- 動作確認用に istio-demo（ambient ラベル付き namespace に httpbin と curl）を別アプリとして用意した。検証を続けるため、apps.yaml には istio / istio-demo を宣言したまま残した
- 実装は Orca のワーカーに任せた。curl から httpbin への通信が ztunnel 経由（HBONE、15008 番）で通ることをログで確認した

## kind クラスタを 3 ノードに作り直し ztunnel のノード間 HBONE を確認

- シングルノードでは送信側と受信側の ztunnel が同じになり、ambient の本来の経路（ノードをまたぐ ztunnel 間の HBONE）を確かめられないため、kind クラスタを control-plane 1 台 + worker 2 台で作り直した（PR #8）
- kind は既存クラスタにノードを追加できないので、クラスタ定義をリポジトリに置いて作り直し、Flux とアプリを入れ直した。クラスタ定義は Flux の同期対象ではないため manifests の外に置いた
- istio-demo の curl と httpbin に podAntiAffinity を付けて別ノードに分け、送信側 ztunnel の outbound と受信側 ztunnel の inbound の両方にログが出ることを確認した
- 実装は Orca のワーカーに任せた

### 申し送り

- マルチノードの kind では control-plane に taint が付くため、Pod は worker 2 台にしか載らない。worker を 1 台に減らすと istio-demo の片方が Pending になる

## Istio の共有 ingress Gateway を追加し istio-demo をホスト名で公開

- Istio の ingress も学ぶため、Gateway API の Gateway で httpbin を外から（メッシュ経由で）アクセスできるようにした（PR #9）
- 最初は istio-demo の中に Gateway を置いたが、実運用ではクラスタで共有する Gateway に各アプリが HTTPRoute をぶら下げる形が一般的なため、istio-ingress を独立したアプリにして共有 Gateway を置く構成に組み替えた
- 共有 Gateway に HTTPRoute を付けられる namespace は、ラベルで明示的に参加したものだけにした（allowedRoutes を Selector にした）
- istio-demo は istio-demo.localhost で振り分けた。*.localhost は /etc/hosts なしで 127.0.0.1 に解決されるため、port-forward と組み合わせてブラウザから開ける
- kind には LoadBalancer がないため、Gateway の Service は ClusterIP にして port-forward で入る
- gateway Pod は ambient の対象外で、Envoy 自身が HBONE を話すため、ログは受信側ノードの ztunnel にだけ出る
- 実装は Orca のワーカーに任せた

### 申し送り

- ローカルの 8080 番は既存の ssh トンネルが使っているため、port-forward は 18080 番を使う
